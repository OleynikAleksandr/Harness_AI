# Версии приложения и Workflow Kit в About

Статус: действующая спецификация scope `application-versions-about-2026-11-13`.
Пользователь выбрал последовательное выполнение без ревьювера и подтвердил
реализацию, проверку нативного About готового приложения и новый GitHub Release.

## 1. Требование и причина

Пользователь показал нативное окно About Harness AI с `0.0.0 (0.0.0)` и
потребовал показывать версию приложения и Workflow Kit, чтобы можно было
проверить, произошло ли обновление.

Согласование: «Я думаю, что там должна быть обязательно и версия самого
приложения и версия Workflow Kit»; «Но где-то же должна быть обозначена
версия приложения и версия workflow kit, иначе откуда я узнаю, что апдейт
произошел?».

Проверено на HEAD `89922ac6`, после закрытия предыдущего scope:

- `package.json.version` равен `0.0.0`;
- `app-bootstrap` не задаёт `setAboutPanelOptions`, используется штатное
  окно Electron с версией и номером сборки из метаданных пакета;
- правило [ReleaseFixes-2026-11-04-2.md, раздел 8](ReleaseFixes-2026-11-04-2.md#8-публикация-на-github)
  задаёт календарные теги `vYYYY.M.D[.N]` и сохранение исходного package.json;
- встроенный Kit соответствует 2.2.4. Его версия и версия приложения —
  разные факты; версия Kit открытого проекта тоже может отличаться;
- установленный Electron 42.5.0 поддерживает `applicationVersion`,
  `version` и `credits` в `setAboutPanelOptions` на macOS; это проверено
  по установленному `electron.d.ts`.

## 2. Видимый результат

Окно About обязательно показывает два раздельно подписанных значения:

- **Harness AI:** полная версия установленного релиза без префикса `v`,
  например `2026.11.13.2`;
- **Workflow Kit:** версия, встроенная именно в это приложение, например `2.2.4`.

Используется штатное окно About. Номер сборки можно показать дополнительно,
но он не заменяет ни одно из двух значений. Дублирующая строка `0.0.0 (0.0.0)`
исчезает. Для среды разработки указывается Development; выдуманного номера
релиза или молчаливого отката к нулевой версии нет.

Информация доступна без открытого проекта. Выбор проекта с другим Kit,
закрытие проекта и отсутствие активной сессии не меняют версии About.

## 3. Источники истины

Версия приложения задаётся **до сборки** явным релизным тегом
`HARNESS_RELEASE_TAG=vYYYY.M.D[.N]`. Не использовать последний существующий
Git-тег: он обычно относится к предыдущему релизу. Не генерировать новый
номер отдельно на этапах упаковки, About и публикации.

Команда упаковки создаёт один неизменяемый дескриптор версии и использует его
для ресурсов приложения, метаданных macOS и последующей публикации:

- `releaseTag`: полный тег GitHub;
- `releaseVersion`: тот же тег без `v`, отображаемый в About;
- `applicationVersion`: три календарных компонента для SemVer и
  `CFBundleShortVersionString`, например `2026.11.13`;
- `buildNumber`: 1 для первого релиза даты, N для суффикса `.N`.

Это явное разделение нужно потому, что календарный тег с суффиксом имеет
четыре числовых компонента, а macOS short version и SemVer — три.

Исходное `package.json.version` вручную не редактируется. Сборщик получает
версию и номер сборки автоматически через параметры electron-builder;
упакованный package.json и Info.plist содержат реальные значения. Это
уточнение прежнего правила «package.json не меняется»: источник остаётся
нетронутым, версия готового продукта перестаёт быть заглушкой.

Core Runtime отдаёт нормализованный `get-product-info` с версией релиза и
версией встроенного Kit. Дескриптор читается из неизменяемого ресурса сборки;
Electron host передаёт только расположение ресурса, не выводит версию сам.
Версия Kit берётся через уже существующий публичный фасад кластера
`workflowKitFacade.installer.version`. Модули Kit и их версия не меняются
ради окна About.

Electron host получает эти факты через Core process bridge и настраивает
нативное окно. Форматирование подписей — представление данных; определение
версий в renderer или host не добавляется. Нового renderer UI и копии
версий в настройках проекта не требуется.

## 4. Сборка и отказы

- `npm run package:mac` использует штатный launcher упаковки и требует
  `HARNESS_RELEASE_TAG`. Пример новой поставки:
  `HARNESS_RELEASE_TAG=v2026.11.13.2 npm run package:mac`.
- Launcher проверяет формат и нормализует номер один раз до сборки.
  Пустой или недопустимый тег прекращает release-сборку с понятной ошибкой.
- При разработке без релизного тега формируется дескриптор Development.
  Отсутствующие, повреждённые или несогласованные релизные метаданные в
  готовом пакете не превращаются в Development или `0.0.0`.
- Повторный dev build не наследует дескриптор старой release-сборки.
- Если Core не может вернуть информацию, About сообщает о недоступности
  данных. Старые значения не используются как подтверждение обновления.
- Публикация берёт тег из проверенного дескриптора созданного пакета.
  Коллизия существующего тега означает пересборку под новым номером,
  а не смену тега после упаковки.

Отдельной архитектуры релизного сервиса, системы настроек или зависимостей
не добавляется. Новый Core-код — строго добавочное поведение существующего
модуля `core-runtime-process`.

## 6. Критерии и проверка

1. Дескриптор, упакованный package.json, Info.plist, ответ Core, About и тег
   публикации согласованы по отображению из раздела 3.
2. Протестированы первая и повторная сборки даты, ошибочные теги, отсутствие
   релизного тега в dev, повреждённые release-метаданные и отсутствие переноса
   старой версии в последующую dev-сборку.
3. Core возвращает информацию без workspace. Наличие проекта с другим
   установленным Kit не подменяет версию Kit приложения.
4. В новой `.app` реально открыто нативное окно About и на снимке читаются
   обе подписанные версии. Проверка только DOM, `setAboutPanelOptions` или
   отдельного JSON не считается доказательством вида нативного окна.
5. Проверены запуск renderer/preload/Core и подготовка временного проекта;
   закрытие About не мешает работе приложения.
6. Проходят существующие проверки коммитов, затем качество, дублирование,
   security и ссылки перед упаковкой; сборки только в delivery-задачах.
7. Номер нового релиза выбран до упаковки; при сборке 2026-11-13 и
   доступности тега ожидается `v2026.11.13.2` (в другой день — дата сборки). Архив и Release соответствуют проверенной сборке, старый
   `v2026.11.13` не перезаписывается.
8. Перед публикацией история проверена на секреты; пользовательская приёмка
   и закрытие выполняются отдельными командами Kit по его правилам.

Проверка пакета использует навыки electron-prototype/electron и временный
профиль. Нативное окно при необходимости снимается средствами захвата окон
macOS; один CDP screenshot renderer не доказывает содержимое About.

план и Workflow Kit configuration вручную не правятся. Дерево модулей не
меняется: новые файлы относятся к существующему `core-runtime-process`.

`docs/evidence/ApplicationVersionsAndAbout-2026-11-13.md`; индекс обновляется
при создании файла. Новый GitHub Release содержит дайджест и zip
неподписанного Harness AI.app, как требует существующий регламент.
