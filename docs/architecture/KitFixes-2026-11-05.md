Статус: спецификация раунда исправлений scope

изменённых модулей и `docs/architecture/workflow-kit/**`.

## 1. Каталоги зависимостей и коммиты

Проблема: коммит задачи QUALITY в `Workflow_Kit` включил 26 МБ
`node_modules`. `quality:apply` с `install` поставил зависимости, каталог
был неотслеживаемым и не игнорировался, и выбор файлов задачи взял его
целиком. Когда пользователь убрал каталог из индекса
(`git rm -r --cached node_modules`) и добавил `node_modules/` в
`.gitignore`, `commit --task` упал: git отказывается добавлять
игнорируемые пути («paths are ignored»).

Исправление:

- Управляемый блок `.gitignore` (`gitignoreSection()`) получает каталоги
  зависимостей: `node_modules/`, `.venv/`, `__pycache__/`. Изменение
  управляемого текста повышает `KIT_VERSION` до 2.2.1;
  `install --update` обновляет блок в установленных проектах. Уже
  отслеживаемые файлы остаются в индексе: их убирают
  `git rm -r --cached <каталог>` и коммитом задачи.
- Подготовка коммита (`stage()` в `git-transaction.ts`):
  - путь из индекса добавляется, как раньше (`git add -A`);
  - путь вне индекса, которого нет на диске, не передаётся в git (нет
    ошибки «pathspec did not match»), его удаление уже в индексе;
  - путь вне индекса, который есть на диске и игнорируется git
    (`git check-ignore --stdin`), тоже не передаётся в git: уже
    подготовленное удаление остаётся в индексе и попадает в коммит, а
    файлы на диске не трогаются.
- Тест: удаление каталога из индекса вместе с добавлением его в
  `.gitignore` коммитится через `commit --task`; путь, которого нет ни в
  индексе, ни на диске, не ломает коммит.

## 2. Проверка `tasks[].checks` при планировании

Проблема: описатель схемы называл `checks` «Extra manual checks». Агент
записал туда текст ручной проверки, план приняли, а `assignment:attach`
(и `task:start`) отказали `CHECK_UNKNOWN`.

Смысл поля: `checks` — id проверок профиля качества
(`quality.checks` в `.harness/workflow/config.json`, включая встроенные
`kit:*`), которые задача запускает сверх обязательных. Обычно это
необязательная проверка (`required: false`), например сборка пакета на
этапе `delivery`. Ручные проверки пишутся в `acceptance`.

Правило проверки (одно для `scope:create`, `scope:propose`,
`scope:choose`, `plan:extend` и `task:update`):

- Проверяются задачи, которые команда создаёт, и задачи, у которых
  меняется `checks`. Старые задачи плана не мешают команде.
- Профиль `CONFIGURED`: каждый id есть среди проверок профиля или
  встроенных защит Kit, которые выполняются всегда
  (`kit:conflict-markers`).
- Профиль не настроен (`DISCOVERY`, до задачи QUALITY): id должен иметь
  форму id проверки (`^[A-Za-z0-9][A-Za-z0-9._:-]*$`, без пробелов).
  Id с префиксом `kit:` должен быть встроенной проверкой Kit. Другие id
  принимаются как проверки, которые задаст QUALITY. `task:start`
  (и `assignment:attach`) сверяет их с настроенным профилем
  (`CHECK_UNKNOWN`), и задачу исправляют `task:update`.
- Отказ — `CHECK_UNKNOWN` с `details {taskId, field, checks, known}`
  (`field` — путь входа, например `tasks[1].checks` или `checks`).
  Подсказка называет `quality:status` и `acceptance` для ручных проверок.
  При отказе ничего не записывается.
- Описатель `schema` описывает поле честно: «Ids of quality checks …»,
  правило вынесено в `rules`.

## 3. Отмена назначения (`assignment:cancel`)

Проблема: назначение, которое застряло (исполнитель не стартовал, worktree
сломан, работа больше не нужна), нельзя снять. `assignment:cleanup`
работает только с `INTEGRATED`, а `assignment:create` отвечает
`ASSIGNMENT_EXISTS`. Оставалось вручную удалять
`.harness/workflow/local/assignments/<id>.json`.

Команда `scripts/workflow assignment:cancel --id <id> [--force]`:

- Работает в main (в worktree исполнителя — `ASSIGNMENT_READ_ONLY`), под
  блокировкой Kit, без незавершённой транзакции и интеграции
  (`TRANSACTION_PENDING`, `INTEGRATION_ACTIVE`).
- Нет записи — `ASSIGNMENT_UNKNOWN`. Запись `INTEGRATED` не отменяется
  (`ASSIGNMENT_INTEGRATED`, подсказка — `assignment:cleanup`).
- Если worktree записи зарегистрирован в git и в нём есть незакоммиченные
  изменения или неотслеживаемые файлы (не игнорируемые), без `--force`
  команда отказывает `ASSIGNMENT_DIRTY` с `details.paths` и ничего не
  меняет. С `--force` worktree удаляется вместе с изменениями.
- Шаги: `git worktree remove` (с `--force` — `-f -f`), `git worktree
  prune`, `git branch -D <ветка>` (ветка назначения удаляется и с
  неинтегрированными коммитами; ответ сообщает её последний коммит для
  восстановления), затем удаление записи. Отказ git на шаге — ошибка
  `ASSIGNMENT_CANCEL_FAILED` с причиной; запись остаётся, команду можно
  повторить.
- План main не меняется: задача остаётся `TODO` и снова готова к выдаче.
- Ответ: `{assignment, worktree, branch, branchTip, task}`; текст
  печатает `next: scripts/workflow assignment:create --task <ID>` (или
  `assignment:next`).

## 4. Отмена застрявшей подготовки коммита (`repair --cancel`)

Проблема: транзакция в фазе подготовки (журнал есть, коммита нет), после
которой изменился индекс, не снималась: `repair --apply` отвечал
`REPAIR_MANUAL` «HEAD, plan or index changed after preparation», а
`repair --cancel` — «The preparation cannot be rolled back automatically».

Исправление `repair --cancel <id>` (для `retry-commit`):

- Подготовка не тронута — откат, как раньше.
- HEAD не изменился, но изменились индекс или план: индекс
  восстанавливается из `index-before` (без копии — из дерева HEAD, без
  коммитов — пустой), план — из журнала (`originalPlan`; файла не было —
  удаляется). Файлы рабочего дерева не трогаются. Журнал, копия индекса и
  ожидающие доказательства убираются, журнал сохраняется как
  `verification/failed-<id>.json`.
- HEAD изменился: `REPAIR_MANUAL` с `details {beforeHead, head}` и
  подсказкой: вернуть HEAD к `beforeHead` (`git reset --soft <sha>`
  сохраняет все изменения) и повторить `repair`, иначе спросить
  пользователя.
- `repair --apply` для `retry-commit` при изменённом состоянии подсказывает
  `repair --cancel <id>` и повтор коммита.
