# Исправления релиза режимов выполнения — 2026-11-04 (раунд 2)

Статус: согласованная спецификация, основа scope `release-fixes-2026-11-04-2`.
Источник: проверка пользователем релиза `execution-modes-2026-11-04` на
`Test_New_HarnesAI_001` и `Test_New_HarnesAI_002`.

Указание пользователя: «остановиться и исправить то, что уже было найдено…
вплоть до сборки нового релиза. И… опубликовать на GitHub… последним в
каждой из последующих план».

Общий принцип: всё, что можно вывести автоматически, не спрашивается у
пользователя. Необязательных и непонятных полей в интерфейсе нет.

## 1. Git-идентичность без терминала

Проблема: при заглушке в настройках Git окно Open Project показало сырой
английский текст с командами терминала, причём дважды. Сообщение Kit и
`nextAction` содержали одни и те же команды, а окно склеило их. Отдельно
пользователь ввёл почту в типографских кавычках `“…”`, и Kit её принял.

Исправление:

- Kit: команда `identity:set --name <имя> --email <почта> --global`.
  Значения проверяются, затем записываются в глобальную настройку Git.
  - Заглушки отклоняются (`GIT_IDENTITY_PLACEHOLDER`).
  - Почта должна иметь вид `локальная-часть@домен.зона`: без пробелов, кавычек
    и угловых скобок. Иначе — `GIT_IDENTITY_INVALID`.
  - Имя не пустое, без кавычек и угловых скобок.
- Сообщение `GIT_IDENTITY_REQUIRED` называет проблему один раз. Команды
  терминала остаются только в `nextAction` для работы без Harness.
- Harness Core:
  - RPC `workflow-identity-set` (имя, почта) вызывает Kit `identity:set`;
  - затем повторяет прерванную подготовку проекта.
- Окно Open/New Project при отказе `GIT_IDENTITY_REQUIRED` показывает форму:
  - пояснение одной строкой: «Git подписывает каждый коммит. Укажите имя и
    почту один раз для всех проектов на этом компьютере»;
  - поля «Имя» и «Почта», кнопка «Сохранить и продолжить».
  - Проверка значений — в Kit; окно показывает его ответ.
- Доктор: проверка `git-identity` без настоящей глобальной идентичности
  открывает ту же форму.

## 2. Open Project без поля имени

Имя проекта при открытии существующей папки — это имя папки. Поле
«Project name» в режиме Open Project убирается. В New Project поле
остаётся: там оно задаёт имя новой папки и обязательно.

## 3. Карточка выбора режима в левом сайдбаре

Карточка показывается в левом сайдбаре под карточкой сессии-владельца, на
месте будущего плана, а не в области диалога. Модель карточки — прежняя
(Core). После выбора на этом месте показывается план с прогрессом.

## 4. Язык новых строк

Строки карточки выбора, панели плана, причин остановки автопилота и окна
подготовки проекта показываются на языке интерфейса. Сейчас в карточке
английские заголовки и кнопки соседствуют с русскими описаниями. Новые ключи
проходят тот же путь локализации, что и существующие строки. Переведённый
пакет обновляется при появлении новых исходных ключей.

## 5. Выбор режима запускает выполнение

Проблема: после выбора `sequential` агент выполнил QUALITY и T001 и закончил
ход по правилу «одна задача — один ход». Автопилот был выключен, и
выполнение остановилось.

Исправление: выбор `sequential` или `orchestrated` в карточке включает
автопилот сессии-владельца (Core). Автопилот сам останавливается:

- на приёмке;
- на блокировке;
- на сборке, которая требует подтверждения;
- в ожидании исполнителей.

Пользователь может выключить автопилот кнопкой, как раньше.

## 6. PATH login-оболочки для процессов агентов

Проблема: приложение, запущенное из Finder, получает урезанный PATH без
`/opt/homebrew/bin`. Проверка Kit `node --test` упала с «Executable not
found», и агенту пришлось дописывать PATH вручную.

Исправление: Core при старте один раз читает PATH login-оболочки
пользователя (`$SHELL -ilc`, с ограничением времени) и объединяет его с
собственным. Процессы провайдеров, их инструменты и команды Kit из Core
получают этот PATH. При ошибке остаётся прежний PATH и пишется диагностика.

## 7. Мелкие исправления

- Управляемый `.gitignore` Kit дополняется `.DS_Store`.
- Встроенная проверка Kit на коммите отклоняет маркеры конфликта
  (`<<<<<<<`, `>>>>>>>`) в добавляемых текстовых файлах
  (`kit:conflict-markers`). В прошлом scope маркеры попали в `module.md`.
- Проверка дублирования рабочего каталога (`check:dup:workspace`)
  игнорирует `.harness/workflow/local/**`. Это локальное состояние Kit.

## 8. Публикация на GitHub

Последняя задача каждого плана начиная с этого — публикация релиза на GitHub
(`delivery`, после сборки).

- Репозиторий: `https://github.com/OleynikAleksandr/Harness_AI`
  (публичный), remote `origin`, ветка `main`.
- Первая публикация:
  - на GitHub лежит автоматический «Initial commit» с лицензией MIT;
  - общей истории с локальной нет;
  - файл `LICENSE` с тем же текстом MIT сначала добавляется в проект задачей
    плана;
  - затем `main` публикуется с `--force-with-lease`, привязанным к этому
    «Initial commit»: он заменяется локальной историей, лицензия
    сохраняется.
  - Merge несвязанных историй не используется: Kit принимает
    двухродительские коммиты только как интеграцию.
- Следующие публикации — обычный `git push` без force.
- Перед каждой публикацией история проверяется на секреты: ключи
  провайдеров, токены, приватные ключи, файлы авторизации.
- Тег — дата сборки `vГГГГ.М.Д` (при повторе в тот же день — суффикс `.N`).
  `package.json` не меняется.
- GitHub Release: тег, заметки из дайджеста раунда, вложение — zip
  неподписанного `Harness AI.app` (`ditto -c -k --keepParent`).
- Проверки этапа push запускает git-хук Kit.
- Правило «публикация — последняя задача плана» записывается в разделе 8
  `AGENTS.md`.
