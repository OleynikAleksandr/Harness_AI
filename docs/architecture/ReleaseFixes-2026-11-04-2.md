## 1. Git-идентичность без терминала

Проблема: при заглушке в настройках Git окно Open Project показало сырой
английский текст с командами терминала, причём дважды. Сообщение Kit и
`nextAction` содержали одни и те же команды, а окно склеило их. Отдельно
пользователь ввёл почту в типографских кавычках `“…”`, и Kit её принял.

### 1.1 Kit (`workflow-git`, `workflow-kit`, `workflow-installer`)

- Команда `identity:set --name <имя> --email <почта> --global`
  (`kit-cli-identity.ts`). Без `--global` — `USAGE`: идентичность задаётся
  один раз для всех проектов. Проект не нужен, команда работает в любой
  папке. Успех — `{name, email, scope: "global"}`, текстом
  `identity: <имя> <<почта>> (global git config)`.
- Один валидатор `isUsableIdentity` и для записи, и для чтения. После
  обрезки пробелов:
  - имя не пустое, без кавычек любого вида (`"`, `'`, `` ` ``, `“`, `”`,
    `„`, `‘`, `’`, `‚`, `«`, `»`, `‹`, `›`) и угловых скобок;
  - почта вида `локальная-часть@домен.зона`: ровно одна `@`, точка в
    домене, без пробелов, кавычек и угловых скобок;
  - нарушение — `GIT_IDENTITY_INVALID`; пропущенный или пустой `--name`
    или `--email` — тоже он;
  - затем заглушки (`isPlaceholderIdentity`) — `GIT_IDENTITY_PLACEHOLDER`.

  Отказы несут только сообщение и `details.field` (`name` или `email`),
  без `nextAction`.
- `writeGlobalIdentity` пишет обрезанные значения через
  `git config --global user.name/user.email`. Глобальный конфиг — тот,
  который читает git (`HOME`, `XDG_CONFIG_HOME`, `GIT_CONFIG_GLOBAL`).
- При чтении (`resolveIdentity`, `install`, проверка Доктора
  `git-identity`) идентичность, не прошедшая валидатор, считается
  заглушкой. Например, почта в типографских кавычках пропускается, а в
  локальном конфиге заменяется.
- Отказ `GIT_IDENTITY_REQUIRED` коммита и установки строит общий
  `identityRequired` (`workflow-git`). Сообщение называет проблему один
  раз: `…; none is set.` или `…; the configured one is a placeholder or
  invalid.` (у установки ещё `Nothing was written.`).
  `details.placeholder` — задана ли идентичность. Команды терминала
  (`git config --global …`, затем `scripts/workflow doctor --fix`) есть
  только в `nextAction`, для работы без Harness.

### 1.2 Core и мост (`workflow-host`, `core-runtime-process`)

- `setIdentity({name, email})` запускает бандл приложения в домашнем
  каталоге, без проекта и `--root`:
  `identity:set --name=<имя> --email=<почта> --global`. Форма
  `--флаг=значение` оставляет значением даже текст, начинающийся с `--`.
- RPC `workflow-identity-set {name, email}`: нестроковые значения —
  `INVALID_REQUEST`, иначе конверт Kit возвращается без изменений.
- Core не хранит прерванную подготовку. После успеха клиент сам повторяет
  тот же запрос `workflow-prepare-project`, который отказал с
  `GIT_IDENTITY_REQUIRED` (тогда ничего не было записано).
- IPC `harness-ai:core:workflow-identity-set`, preload
  `setGitIdentity({name, email})`.

### 1.3 Интерфейс (`project-setup-dialog`, `project-doctor-panel`)

- Окно Open/New Project при отказе `GIT_IDENTITY_REQUIRED` вместо ошибки
  показывает форму (`GitIdentityForm`):
  - пояснение одной строкой: «Git подписывает каждый коммит. Укажите имя и
    почту один раз для всех проектов на этом компьютере»;
  - поля «Имя» и «Почта», кнопка «Сохранить и продолжить».
- Форма передаёт введённые значения без изменений, проверяет их Kit. Отказ
  (`GIT_IDENTITY_INVALID`, `GIT_IDENTITY_PLACEHOLDER`) показывается одним
  сообщением под полями. После успеха окно само повторяет тот же запрос
  подготовки: та же папка, имя и флаг `install`.
- Прочие ошибки: сообщение Core, затем `nextAction` отдельной строкой,
  если сообщение его ещё не содержит (`failureText`). Команды больше не
  дублируются.
- Доктор: проверка `git-identity`, которая падает и не исправляется (нет
  настоящей глобальной идентичности), показывает ту же форму вместо команд
  терминала. После сохранения панель запускает Доктор с `fix: true`: он
  копирует глобальную идентичность в конфиг репозитория, и панель
  показывает новый отчёт.

## 2. Open Project без поля имени

Имя проекта при открытии существующей папки — это имя папки. В режиме
Open Project поля «Project name» нет (`asksProjectName(mode)`), запрос не
передаёт `name`, и Kit называет проект по папке. В New Project поле
остаётся: там оно задаёт имя новой папки и обязательно.

## 3. Карточка выбора режима в левом сайдбаре

- Карточка показывается в левом сайдбаре под карточкой сессии-владельца
  (`card.sessionId`), на месте плана (`OwnerPlanSlot` дерева сессий).
  Модель карточки и маршрут нажатия — прежние (Core). Фасад сайдбара один
  раз на workspace вызывает `useExecutionModeCard` и передаёт дереву
  `{card, choose}`.
- Пока карточка `offered` или `saving`, план владельца не показывается.
  После выбора (`chosen`) короткая строка выбора стоит над планом с
  прогрессом, пока Core не удалит карточку в конце следующего хода агента.
  Карточка `dismissed` и владелец вне списка сессий карточки не дают.
- Вёрстка рассчитана на узкий сайдбар: в строке варианта название с
  пометкой, описание и причина стоят над кнопкой во всю ширину. Длинный
  текст переносится, горизонтальной прокрутки нет.
- В области диалога карточки больше нет. Отдельные окна сессий, у которых
  нет сайдбара, её не показывают.

## 4. Язык новых строк

Проблема: в карточке английские заголовки и кнопки соседствовали с русскими
описаниями. Причина — настройки пользователя: «UI Labels» = английский,
«UI Helper Text» = русский. Строки карточки уже имели ключи и переводы.

Решение (`localization-runtime`):

- Новые ключи карточки, панели плана, причин остановки автопилота, окна
  подготовки проекта и формы Git-идентичности проходят обычные категории.
  Заголовки и кнопки — `ui_labels`, они следуют настройке «UI Labels»;
  пояснения — `ui_helper_text`, они следуют «UI Helper Text». Язык строки —
  язык, настроенный для её категории.
- Обновление пакета инкрементальное. Файл пакета хранит `sourceEntries` —
  английский исходный текст каждой переведённой записи. В движок перевода
  уходят только новые, изменённые, отсутствующие и ранее неудачные ключи.
  Смена движка, файл старого формата без `sourceEntries` или `force`
  переводят весь пакет заново.
- Сбой движка не кэшируется. Неудачные записи остаются английскими, пакет
  сообщает `error` и при следующем проходе повторяет только их. Кэш
  bootstrap-пакета пишется, только если ни у одного пакета нет ошибки.

## 5. Выбор режима запускает выполнение

Проблема: после выбора `sequential` агент выполнил QUALITY и T001 и закончил
ход по правилу «одна задача — один ход». Автопилот был выключен, и
выполнение остановилось.

Исправление:

- После успешного `scope:choose` для `sequential` и `orchestrated` Core
  включает автопилот сессии-владельца до отправки сообщения выбора:
  `setEnabled(владелец, true, {evaluate: false})`. Оценки и собственного
  хода автопилота при этом нет. Событие `workflow:autopilot` сразу
  показывает переключатель включённым.
- Сообщение выбора — следующий ход агента. Его начало задаёт исходную точку
  автопилота, а конец хода решает, продолжать ли план.
- `refine` и отказ Kit (например `PROPOSAL_CHANGED`) автопилот не меняют.
- Автопилот сам останавливается по обычным причинам:
  - на приёмке;
  - на блокировке;
  - на сборке, которая требует подтверждения;
  - в ожидании исполнителей или выбора режима.
- Пользователь может выключить автопилот кнопкой, как раньше.

## 6. PATH login-оболочки для процессов агентов

Проблема: приложение, запущенное из Finder, получает урезанный PATH без
`/opt/homebrew/bin`. Проверка Kit `node --test` упала с «Executable not
found», и агенту пришлось дописывать PATH вручную.

Исправление (`core-login-path.ts`): до `initialize()` вход процесса Core
один раз ждёт `applyLoginShellPath()`.

- На macOS и Linux запускается `$SHELL -ilc` (без `SHELL` — `/bin/zsh` на
  macOS, иначе `/bin/bash`): без stdin, отдельной группой процессов.
  Через 3 с группа завершается принудительно.
- PATH читается между уникальными маркерами, поэтому вывод rc-файлов не
  мешает.
- Новый `process.env.PATH`: записи login-оболочки, затем недостающие
  унаследованные, затем существующие на macOS `/opt/homebrew/bin` и
  `/usr/local/bin`.
- Процессы провайдеров, их инструменты и команды Kit из Core наследуют
  этот PATH.
- При ошибке остаётся унаследованный PATH (с теми же каталогами macOS) и
  пишется одна строка диагностики. На Windows шаг пропускается.

## 7. Мелкие исправления

- `KIT_VERSION` 2.1.1: управляемая секция `.gitignore` дополнена
  `.DS_Store`. Установки 2.1.0 читаются как `KIT_OUTDATED`, обновление
  добавляет строку.
- Встроенная проверка `kit:conflict-markers` (этап `commit`,
  обязательная):
  - каждый существующий текстовый файл кандидата отклоняется, если строка
    начинается с `<<<<<<< ` или `>>>>>>> ` (файлы с байтом NUL
    пропускаются);
  - в таком файле сообщается и строка ровно `=======`. Одиночная
    `=======` (подчёркивание заголовка Markdown) проходит;
  - вывод — `<файл>: line(s) <n, …>`;
  - её выполняет каждый коммит, служебные (DOCS, QUALITY, `scope-plan` и
    другие) тоже;
  - новая конфигурация содержит её явно. Конфигурация, записанная до неё,
    получает её неявно: Kit добавляет её последней в выбор этапа `commit`,
    если ни одна проверка не имеет того же id или builtin. Файл
    конфигурации не переписывается.

  В прошлом scope маркеры попали в `module.md`.
- Проверка дублирования рабочего каталога (`check:dup:workspace`)
  игнорирует `.harness/workflow/local/**`. Это локальное состояние Kit.

## 8. Публикация на GitHub

Последняя задача каждого плана начиная с этого — публикация релиза на GitHub
(`delivery`, после сборки).

- Репозиторий: `https://github.com/OleynikAleksandr/Harness_AI`
  (публичный), remote `origin`, ветка `main`.
- Первая публикация:
  - на GitHub лежит автоматический «Initial commit» с лицензией MIT;
  - общей истории с локальной нет;
  - файл `LICENSE` с тем же текстом MIT сначала добавляется в проект задачей
    плана;
  - затем `main` публикуется с `--force-with-lease`, привязанным к этому
    «Initial commit»: он заменяется локальной историей, лицензия
    сохраняется.
  - Merge несвязанных историй не используется: Kit принимает
    двухродительские коммиты только как интеграцию.
- Следующие публикации — обычный `git push` без force.
- Перед каждой публикацией история проверяется на секреты: ключи
  провайдеров, токены, приватные ключи, файлы авторизации.
- Тег — дата сборки `vГГГГ.М.Д` (при повторе в тот же день — суффикс `.N`).
  `package.json` не меняется.
- GitHub Release: тег, заметки из дайджеста раунда, вложение — zip
  неподписанного `Harness AI.app` (`ditto -c -k --keepParent`).
- Проверки этапа push запускает git-хук Kit.
- Правило «публикация — последняя задача плана» записывается в разделе 8
  `AGENTS.md`.
