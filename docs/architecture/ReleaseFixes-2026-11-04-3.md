# Исправления раунда 3 — 2026-11-04: контекст агента, пауза, проекты

Статус: согласованная спецификация, основа scope `release-fixes-2026-11-04-3`.
Источник: обсуждение с пользователем после релиза `v2026.11.4`.

Указание пользователя: «Закрывая предыдущие составляй новую спецификацию и
to-do plan, и выполняя её вплоть уже до публикации на GitHub».

Общие принципы:

- Всё, что нужно агенту для работы, Kit передаёт текстом в самом промпте.
  Ссылка на файл допустима только как происхождение или цель записи
  (`AGENTS.md` §3). Молчаливой обрезки текста нет.
- Состояние процесса (пауза, автопилот) — правда Kit и Core. Интерфейс
  только показывает её и передаёт нажатия.

Перед scope Kit самого репозитория `harness-ai` обновлён командой
`install --update` с 2.0.0 до 2.1.1 (коммит `053fc395`, роль `kit-update`).
Метки `host` у репозитория нет: он развивается из Claude Code, scope
создаётся без карточки выбора режима.

## 1. Схемы входного JSON

Проблема: агент получает только имена команд (`--input <file.json>`) и
восстанавливает форму JSON по коду `workflow.mjs`. Лимиты дайджеста
(`result` ≤ 600 байт, ≤ 8 пунктов по ≤ 300 байт) нигде не названы заранее.

Исправление:

- Описатели входа — данные, а не текст в документации: модуль
  `plan-input-schema.ts` в `workflow-plan` (вход `scope:create`,
  `scope:propose`, `plan:extend`, `task:update`, `carryover`, дайджест
  `commit --digest`) и `quality-input-schema.ts` в `workflow-quality`
  (профиль `quality:apply`). Описатель поля: имя, тип, обязательность,
  лимиты в байтах и количестве, допустимые значения, код отказа. Лимиты
  берутся из тех же констант, что у валидаторов. Межполевые правила и
  правила состояния плана (порядок зависимостей, раунд, ревизия) остаются
  в валидаторах и перечислены в описателе строками `rules`.
- Контрактные тесты не дают описателю и валидатору разойтись:
  - пример из описателя проходит валидатор;
  - удаление каждого обязательного поля даёт код из описателя;
  - превышение каждого лимита даёт код из описателя и `details.field`.
- Отказы на вход называют поле: валидаторы, у которых нет
  `details.field`, получают его.
- Команда `scripts/workflow schema <команда>` печатает описатель и
  короткий пример; без аргумента — список команд со схемами. Работает и в
  worktree исполнителя.
- Пакет восстановления несёт схему следующего шага в разделе `schema`
  (компактный текст и пример):
  - нет scope — вход `scope:propose` или `scope:create` (по метке `host`);
  - задача QUALITY — профиль `quality:apply`;
  - задача DOCS — дайджест с лимитами;
  - scope `READY_FOR_ACCEPTANCE` или раунд исправлений — вход
    `plan:extend`.

## 2. Текст документов в поручении и пакете

Проблема: поручение исполнителю (`assignment:create`) перечисляет
`context` задачи путями, без текста. Пакет восстановления при нехватке
бюджета заменяет документ строкой «прочитайте файл». Исполнитель читает
документы через Read, а большие — в несколько заходов.

Исправление:

- Поручение несёт полный текст каждого документа из `context` задачи в
  маркерах:

  ```text
  <document path="docs/spec.md" bytes="1234">
  …текст…
  </document>
  ```

  Ссылка с `heading` вставляет только этот раздел (тот же поиск раздела,
  что в пакете), в маркере добавляется `heading="…"`. Если у задачи нет
  `context`, вставляется спецификация scope.
- Бюджет поручения — `budget.briefBytes` конфигурации (по умолчанию
  60 000 байт; старые конфигурации получают значение по умолчанию без
  перезаписи файла).
- Проверка при создании плана: `scope:create`, `scope:propose`,
  `plan:extend` и `task:update` считают для каждой задачи размер её
  `context` (или спецификации). Превышение бюджета — отказ
  `CONTEXT_TOO_LARGE` с `details {taskId, bytes, budget}` и подсказкой
  сузить `context` до разделов (`heading`). Отсутствующий файл —
  `CONTEXT_MISSING`.
- `assignment:create` повторяет проверку на текущих файлах: документ мог
  вырасти. Превышение — тот же отказ, назначение не создаётся.
- Пакет восстановления: обязательные документы текущей задачи всегда
  вставляются текстом (целиком или нужным разделом), даже сверх бюджета
  пакета. Тогда пакет помечается `overBudget`, а необязательные разделы
  уходят первыми. Строки «read the file» для обязательного документа
  больше нет.

## 3. Дополнительный контекст без чтения кусками

### 3.1 Команда `context`

`scripts/workflow context <path>[#Раздел] …` печатает тексты в тех же
маркерах.

- Бюджет ответа 28 000 байт: вывод команды в Claude Code обрезается около
  30 000 символов.
- Документы отдаются целыми по порядку, пока помещаются. Не вошедшие
  перечисляются в конце с размером: агент запрашивает их следующим
  вызовом.
- Документ больше бюджета отдаётся по разделам второго уровня.
  `#Раздел` выбирает раздел по тексту заголовка или его slug.
- Путь вне проекта, каталог Kit (`.harness/workflow/**`) или не
  текстовый файл — отказ.
- `--list [<каталог>]` печатает карту: путь, размер в байтах, заголовки
  второго уровня.
- Команда разрешена в worktree исполнителя.

### 3.2 Карта документации

Пакет восстановления и поручение несут раздел `documents`: карта
Markdown-файлов проекта без текста (путь, байты, заголовки второго
уровня).

- Сначала идут документы каталога спецификации scope, затем остальные.
- Бюджет карты 4 000 байт. Хвост заменяется строкой «ещё N документов:
  `scripts/workflow context --list`».
- Каталоги `node_modules`, `.git`, `.harness/workflow` и игнорируемые git
  файлы в карту не входят.

### 3.3 Размер документов и управляемый текст

- `doctor` получает проверку `doc-size`: все Markdown-файлы проекта (не
  только изменённые) не больше `budget.documentBytes`. Нарушение —
  предупреждение со списком файлов: такой документ нельзя прочитать за
  один Read, его нужно разделить.
- Управляемый раздел `AGENTS.md`:
  - строки о `schema` и `context`;
  - запрет читать служебные файлы Kit (`.harness/workflow/runtime/**`),
    сгенерированный код, логи и транскрипты: нужное из них даёт Kit.
- Изменение управляемого текста повышает `KIT_VERSION` до 2.2.0.

## 4. Автопилот по умолчанию и пауза

Проблема: автопилот выключен по умолчанию и включается переключателем в
верхней полосе. Пользователь хочет, как в Workflow Pilot, кнопку паузы в
самом плане.

### 4.1 Пауза — состояние Kit

- Kit: `scripts/workflow pause:set --on|--off --note "<слова
  пользователя>"`. Состояние хранится в
  `.harness/workflow/local/pause.json` и переживает перезапуск приложения.
- `status` и `autopilot:status` показывают `paused`.
- На паузе `task:start` в main отклоняется (`WORKFLOW_PAUSED`), и
  `assignment:create` тоже. Задачи уже выданных назначений исполнители
  доводят до конца: в worktree исполнителя пауза не действует.
- Пауза не мешает `commit`, интеграции, `accept`, `repair` и чтению.

### 4.2 Core

- Автопилот включён по умолчанию для каждой подходящей сессии
  (`initialState` с `enabled = true`). Собственные остановки остаются:
  нет scope, приёмка, блокировка, delivery с подтверждением, ожидание
  исполнителей, лимит продолжений.
- Новая причина остановки `paused` (из `autopilot:status`) — в общем
  списке остановок перед остальными причинами scope.
- RPC `workflow-pause-set {sessionId, paused}`:
  - `paused: true` — Kit `pause:set --on`; текущий ход агента не
    прерывается;
  - `paused: false` — Kit `pause:set --off`, затем немедленная оценка
    автопилота сессии-владельца (продолжение, если агент свободен).
- Модель отображения — поле `pauseState` в снимке автопилота, выводится в
  Core:
  - `running` — паузы нет;
  - `pausing` — пауза поставлена, ход агента ещё идёт или задача
    `IN_PROGRESS`;
  - `paused` — пауза, агент свободен.
- Переключатель `workflow-autopilot-set` больше не нужен интерфейсу. RPC
  остаётся для внутренних вызовов; мост и preload его не публикуют.

### 4.3 Интерфейс

- Переключатель автопилота убирается из верхней полосы
  (`workflow-status-strip`). Строка статуса остаётся.
- Панель плана в сайдбаре показывает кнопку по `pauseState`:
  - `running` — «Пауза»;
  - `pausing` — «Пауза после текущей задачи», неактивна;
  - `paused` — «Продолжить».
- Строки проходят локализацию (`ui_labels`).

## 5. Git-идентичность в процессах агентов

Проблема: процессы Claude получают `HOME` = домашняя папка провайдера
(`~/.harness-ai/providers/claude/home`), Kimi — свою. Там нет
`~/.gitconfig`. Агент, который сам ставит Kit в новую папку, получает
`GIT_IDENTITY_REQUIRED`, хотя глобальная идентичность настроена.

Исправление: чистая функция в `provider-home-manager`. Если `HOME`
окружения переопределён, `GIT_CONFIG_GLOBAL` не задан и настоящий
`~/.gitconfig` существует, она добавляет `GIT_CONFIG_GLOBAL=<настоящий
home>/.gitconfig`. Функция вызывается:

- в `getAuthEnvironment()` Claude (покрывает SDK, захват запросов и
  перевод);
- при запуске процесса Kimi (`kimi-acp-session-process.ts`), когда
  передан `HOME`.

Codex и Grok `HOME` не переопределяют и не меняются.

## 6. Без встроенного проекта

Проблема: путь к репозиторию разработчика зашит в Core как встроенный
проект `harness-ai-local`. Его нельзя удалить, и пользователь случайно
запускает сессии в репозитории самого Harness.

Исправление:

- Core: реестр проектов может быть пустым, активного проекта может не
  быть.
  - Встроенный проект и сессия `Harness AI bootstrap` из реестра сессий
    удаляются.
  - Сохранённая запись `harness-ai-local` в `workspaces.json` становится
    обычным проектом и удаляется как любой другой.
  - Без активного проекта адаптеры провайдеров не регистрируются, а
    запросы, которым нужен проект, получают отказ `NO_WORKSPACE`.
  - Удаление активного проекта делает активным первый оставшийся или
    оставляет реестр пустым.
- Интерфейс без проекта показывает начальный экран с Open Project и New
  Project. Меню проектов позволяет удалить любой проект.
