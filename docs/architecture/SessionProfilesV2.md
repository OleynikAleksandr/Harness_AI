# Профили сессий v2: единый документ и инвентарь инструментов

Ревизия контракта `docs/architecture/SessionProfiles.md`. Документ — база
для следующего todo-plan. Согласовано с пользователем в чате 2026-07-02;
раздел «Открытые вопросы» намеренно не закрыт и будет дополнен после
отдельного обсуждения (Codex/Kimi).

## Мотивация: что сломано в v1

1. **Категорийный whitelist девальвирует универсальные профили.** Словарь
   v1 из шести категорий (`file-read`, `file-write`, `shell`, `web`, `git`,
   `tests`) транслируется у Claude в исчерпывающий whitelist
   (`options.tools = string[]`): установленный
   `@anthropic-ai/claude-agent-sdk` 0.3.198 документирует `tools: string[]`
   как «базовый набор доступных built-in инструментов целиком» — всё, чего
   нет в массиве, недоступно. Реальный native-стек Claude Code 2.1.198
   (прокси-дамп пользователя, CodeAI-Hub,
   `Claude_System_Tools_2026-04-24T13-55-05-221Z.md`) содержит **10
   инструментов**: `Agent`, `Bash`, `Edit`, `Glob`, `Grep`, `Read`,
   `ScheduleWakeup`, `Skill`, `ToolSearch`, `Write` (и в этом дампе нет
   `WebSearch`/`WebFetch` — наличие web-инструментов зависит от билда).
   Карта категорий v1 знает только 8 имён, поэтому managed-профиль **молча
   и всегда** отрезает `Agent`, `Skill`, `ToolSearch`, `ScheduleWakeup` —
   при любых настройках `tooling.yaml`. Пользовательский вердикт: «так
   делать нельзя».
2. **Выбирать не из чего.** Фиксированный словарь не отражает фактический
   перечень инструментов установленной версии SDK/CLI. При создании профиля
   пользователь должен видеть реальную выборку инструментов провайдера, а
   не выдумывать имена.
3. **Три файла на профиль неудобны.** Правка профиля сегодня — это три
   документа (`profile.yaml`, `system-prompt.md`, `tooling.yaml`). Нужен
   один документ с секциями, которые умеет читать ядро.

## Решения v2 (согласовано 2026-07-02)

### 1. Единый документ профиля

- Один профиль = один файл `~/.harness-ai/Profiles/<id>.md`
  (`HARNESS_AI_HOME` учитывается, как раньше). Директории-на-профиль больше
  нет; `id` — имя файла без расширения (kebab-case).
- Формат: **YAML frontmatter + тело-промпт**. Метаданные и тулинг лежат
  «шапкой» между `---`, всё тело файла после frontmatter — системный промпт
  как есть (байт в байт, без служебных маркеров в теле — промпт может
  содержать любые заголовки, коллизии исключены по построению):

  ```markdown
  ---
  name: Review
  description: Code and architecture review.
  # provider: claude        <- только у индивидуального профиля
  tooling:
    ScheduleWakeup: off        # имя есть только в инвентаре Claude
    web_search: off            # имя есть только в инвентаре GLM Native
    Bash@claude: off           # явная метка провайдера (сужение)
  ---

  # Review workflow

  Текст системного промпта без ограничений...
  ```

- Frontmatter парсится тем же пакетом `yaml`, что и v1-документы. VS Code
  подсвечивает frontmatter из коробки; «Edit in VS Code» открывает один
  файл.
- Валидация: отсутствующий/битый frontmatter, пустое `name` или пустое
  тело-промпт — профиль invalid с человекочитаемыми issue (как в v1).
- **Clean break, без совместимости** (решение пользователя: приложение
  single-user). Трёхфайловый формат удаляется полностью: парсер v1,
  раскладка директорий, сиды и authoring переходят на единый файл. Переход:
  удалить (или переименовать) старый корень `~/.harness-ai/Profiles` —
  first-access seeding пересоздаст стандартный набор уже в новом формате;
  собственные тексты пользователь переносит копипастой.

### 2. Provider Tool Inventory (инвентарь инструментов провайдера)

Новый Core-модуль в кластере `session-profiles` (рабочее имя
`tool-inventory`): read model фактического перечня инструментов провайдера
в установленной версии.

- **Claude**: источник — system-сообщение `init` SDK
  (`subtype: "init"`, поля `tools: string[]` и `claude_code_version`;
  `sdk.d.ts:4101` в 0.3.198). Снятие:
  - пассивно — Core обновляет кэш инвентаря при каждом `init` живой сессии;
  - активно (probe) — когда кэша нет или версия CLI сменилась, по запросу
    инвентаря Core поднимает лёгкую native-сессию SDK, читает `init` и
    закрывает её, чтобы выборка была доступна в Profile Creator ещё до
    первой пользовательской сессии.
- **GLM client / Kimi client / OpenRouter / Local Models**: после
  universal-client migration старые GLM Native и Kimi ACP адаптеры удалены;
  инвентарь и synthetic-native application для client-four входят в Phase 5
  и строятся вокруг live `*-client` ids, а не retired ids.
- **Codex**: канал получения инструментов остаётся отдельным native-путём;
  managed-профили Codex остаются prompt-only до dedicated application layer.
- Кэш инвентаря — локальный runtime state в Harness home (не tracked),
  ключ — `<providerId>@<версия>`.
- RPC для UI: `get-provider-tool-inventory` → `{ version, tools[] }` на
  провайдера (плюс признак «инвентарь недоступен» для провайдеров без
  канала).

### 3. Семантика применения: «vendor-набор минус off»

- Словарь категорий v1 **удаляется полностью** (парсер, шесть категорий,
  карты категорий в адаптерах Claude/GLM).
- `tooling:` во frontmatter — **плоский список точных имён инструментов**
  со значением `off` (deny-list), общий для всех провайдеров (ревью
  пользователя 2026-07-02: универсальный профиль — первичная модель;
  индивидуальное применение собирается из общего документа, а не из шести
  почти одинаковых копий). Правило резолюции имени:
  - имя **без метки** действует у каждого провайдера, в чьём инвентаре
    такое имя есть (общие и уникальные имена «просто работают»);
  - имя **с меткой `@<providerId>`** (например `Bash@claude`) действует
    только у этого провайдера — для явности и на случай коллизии, когда
    одноимённые инструменты разных провайдеров надо выключать раздельно
    (на практике имена не пересекаются: PascalCase у Claude, snake_case у
    GLM Native).
  Всё не упомянутое — включено, в том числе новые инструменты, появившиеся
  после обновления SDK: они больше не пропадают молча. Явное `on` разрешено
  как самодокументирующий no-op. Профиль без секции `tooling:` даёт каждому
  провайдеру полный vendor-набор.
- Применение адаптерами:
  - **Claude (managed)**: prompt заменяется, как раньше; вместо
    исчерпывающего `tools` передаётся `disallowedTools: [выключенные]`
    (`sdk.d.ts:1327`), базовый набор инструментов остаётся vendor-набором.
  - **GLM Native (managed)**: уже deny-семантика
    (`filterGlmWorkflowTools`); карта категорий заменяется на точные имена.
  - **Native-профиль**: без изменений — никакого вмешательства в канал.
- Контракт payload: `SessionProfilePayload.toolingCategories` заменяется на
  `deniedTools: string[]` — Core (материализатор) при создании сессии
  вычисляет deny-список конкретного провайдера из плоского списка по
  правилу резолюции (имя без метки + имена с меткой этого провайдера);
  immutable applied snapshot сессии сохраняется, как в v1 (правка профиля
  влияет только на новые сессии).
- Имя инструмента, отсутствующее в текущем инвентаре, — **предупреждение в
  UI, а не invalid**: профиль не должен ломаться от смены версии SDK
  (инструмент мог исчезнуть или ещё не появиться).

### 4. Profile Creator: выборка инструментов

- Уточнение 2026-07-09: первый реализуемый scope Profile Creator больше не
  создаёт универсальные профили. Новый профиль всегда provider-scoped, форма
  требует provider id, а список провайдеров покрывает все active Core ids
  (`claude`, `codex`, `codex-uc`, `kimi-client`, `glm-client`,
  `openrouter-client`, `local-models-client`). Universal-профили остаются
  только legacy/read-only данными, если пользовательские старые файлы ещё
  лежат на диске.
- При создании и редактировании профиля UI показывает фактическую выборку
  инструментов из инвентаря Core: чекбокс-список своего провайдера.
- Данные выборки приходят только из Core RPC (инвентарь — Core read model);
  renderer не выводит перечни сам (Core Authority).
- Правка файла в VS Code остаётся первоклассным путём: live refresh каталога
  по файловому watcher уже работает
  (`session-profiles-live-refresh-2026-07-02`).
- Для провайдера без инвентаря (Codex/Kimi до закрытия открытого вопроса)
  UI честно показывает «инвентарь недоступен» вместо пустой выборки.

### 5. Съём native-эталонов: системные промпты и тулинг провайдеров

Для составления кастомных профайлов нужны **native-эталоны** — фактические
системные промпты и полные схемы инструментов провайдеров — в виде
текстовых документов читаемого формата (согласовано 2026-07-02).

> Анатомия снятого промпта (два слоя: статичная кэшируемая обвязка vs живой
> контекст сессии), prompt caching, поблочный разбор Claude/Codex/Kimi, модель
> B2 (замороженная обвязка из папки Profiles + общий генератор живого
> контекста), решение по балласту Claude `# Memory` и потолки применения по
> провайдерам вынесены в отдельный документ:
> `docs/architecture/NativePromptComposition.md` (Phase 7 — Native Profile
> Unification).

- **Отдельный самостоятельный кластер** `provider-network-capture` в Core
  Runtime (не часть кластера `session-profiles`): это диагностический
  инструмент над приложением, полезный сам по себе, а session-profiles v2 —
  лишь один из его потребителей. Кластер владеет прокси, диагностическим CA,
  writer'ом и оркестрацией capture; провайдер-специфичный env-инъекшн живёт
  в адаптерах провайдеров (provider-runtime). **Провайдеры в scope: Claude,
  Codex, Kimi** (Kimi — полноправный, не отложенный). GLM Native съёма не
  требует.
- **Выбор модели в capture обязателен**: у разных моделей одного провайдера
  реально разные системные промпты, поэтому capture параметризуется
  `(provider, model)` (и reasoning, где применимо); список моделей берётся
  из Core-owned `provider-descriptor`, а не выдумывается UI.
- **Решение: перенести поведение реализованной архитектуры CodeAI-Hub
  «Provider Native Request Capture»** (reference: релиз `1.2.62`,
  `packages/core/src/provider-network-capture/**` + архивный план
  `Plans/Archive/Provider_Native_Request_Capture_Architecture.md`) в новые
  модули Harness AI (по правилам AGENTS.md — переносим поведение, не
  копируем пакет). Открытый [claude-tap](https://github.com/liaohch3/claude-tap)
  остаётся внешним кросс-чеком, но основой служит наш проверенный в бою
  вариант: дампы 2026-04-24 (`Claude_System_Tools_*`,
  `codex-native-*`) сделаны именно им.
- **Модель съёма — forward-транзит с записью запроса** (пересмотр
  2026-07-03; прежний capture-and-abort оказался несовместим с обязательным
  WebSocket-транспортом Codex, см. ниже): локальный CONNECT-прокси
  (127.0.0.1) с диагностическим CA терминирует TLS клиента и **форвардит
  запрос на реальный upstream**, записывая запрос (и, где дёшево, ответ).
  Для HTTP-провайдеров (Claude, Kimi) читается тело запроса напрямую; для
  Codex WS-транспорта прокси завершает `101`-upgrade с реальным сервером,
  при пересылке upgrade-запроса **вырезает `Sec-WebSocket-Extensions`**
  (сервер не согласует `permessage-deflate` → клиентские фреймы приходят
  несжатым текстом), декодирует первый клиентский text-фрейм
  `{"type":"response.create","instructions":..,"tools":..,"input":..}` и
  извлекает `instructions` (system), `tools`, `input` (messages), затем
  обрывает поток. **Trade-off vs прежний capture-and-abort:** запрос теперь
  ДОХОДИТ до вендора (upgrade завершается, probe-turn стартует) — это цена
  за захват WS-транспорта, иначе недоступного; probe-turn короткий, обрыв
  сразу после захвата фрейма минимизирует генерацию и стоимость.
  Детерминированный probe-промпт помечает запрос как диагностический; фильтр
  целей отделяет модельный запрос (`api.anthropic.com`,
  `chatgpt.com/backend-api/codex/...`) от фоновых.
- **Подключение клиентов**: Claude — интерактивный запуск провайдер-бинаря
  в pty (см. Claude-блок ниже) с env `HTTPS_PROXY` + `NODE_EXTRA_CA_CERTS`
  (Node TLS); Codex — изолированный временный app-server c `HTTPS_PROXY` +
  `SSL_CERT_FILE` (Rust TLS), рабочий app-server не мутируется. **Kimi
  УДАЛЁН из capture (2026-07-05, вместе с модулем `kimi-provider`)** — прежде
  он снимался через **reverse-forward мост** (бинарь kimi Mach-O игнорирует
  proxy-env); этот путь удалён, capture обслуживает только Claude/Codex.
  GLM Native и остальные endpoint-модули универсального клиента съёма не
  требуют: их системное сообщение и схемы инструментов собирает наш
  собственный клиент.
- **Codex: WebSocket-транспорт обязателен и неотключаем** (эмпирически
  установлено 2026-07-03 диагностическими прогонами против реального
  app-server 0.142.5): Codex форсит WebSocket для `/backend-api/codex/responses`
  (`openai-beta: responses_websockets=2026-02-06`, `Upgrade: websocket`), и
  отключить его нельзя — `--disable responses_websockets`/`_v2` **не
  переключает** транспорт (работало на старых версиях, на которые опирается
  claude-tap; на 0.142.5 мертво), а `-c model_providers.openai.supports_websockets=false`
  отклоняется (`openai` — зарезервированный built-in id). Payload едет в
  WS-фреймах после `101`, поэтому capture-and-abort в принципе не может его
  прочитать (обрыв рвёт соединение до фреймов). Решение — forward-транзит с
  декодированием WS-фрейма (см. модель съёма выше): подтверждено рабочим —
  извлечён полный Codex system prompt + tools из первого клиентского
  text-фрейма. Важно: claude-tap нативного WS-захвата НЕ имеет (их незакрытый
  TODO), так что готового решения оттуда нет; взят его forward-подход плюс наш
  трюк со срезанием `Sec-WebSocket-Extensions`. Системный промпт дополнительно
  дублируется в rollout-логе (`base_instructions`) как diagnostic context, но
  схемы инструментов существуют только в теле запроса — без чтения WS-фрейма
  пара неполна. **Выбор нужного фрейма** (уточнено 2026-07-03 после повторного
  захвата): недостаточно фильтра `bodyIncludes` (probe-текст) — фоновый
  `memory_consolidation` turn консолидирует НАШУ probe-сессию, поэтому probe
  попадает и в его `input`, и prewarm-фрейм (пришедший первым) ложно
  сматчивается. Дискриминатор — число инструментов: probe-turn несёт полный
  нативный набор (17 tools), memory-consolidation фрейм — `tools: []`. Поэтому
  Codex-правило требует `minimumToolCount: 1` (проброшено в WS-захват как
  `minimumTools`), и захватывается фрейм probe-turn, а не prewarm.
- **Codex: слои инструментов (что реально попадает в эталон)** (эмпирически
  2026-07-03): нативный **inline-набор в `response.create` — 17 инструментов**
  (`exec_command`, `write_stdin`, `list_mcp_resources`,
  `list_mcp_resource_templates`, `read_mcp_resource`, `update_plan`,
  `request_user_input`, `list_available_plugins_to_install`,
  `request_plugin_install`, `apply_patch`, `view_image`, `get_goal`,
  `create_goal`, `update_goal`, `tool_search`, `web_search`,
  `image_generation`). Это полный inline-контракт запроса — то, что модель
  получает в системном запросе. **Feature-флаги app-server НЕ добавляют
  инструменты**: включение `--enable browser_use/computer_use/in_app_browser/
  apps/multi_agent/memory_tool` оставляет тот же набор из 17. Инструменты
  `browser_use`/`computer_use` и tools MCP-серверов (playwright, node_repl/
  cua_node из `config.toml`) живут в **отдельном слое**: они приходят от
  MCP-серверов (медленный старт, у `node_repl` `startup_timeout_sec = 120`)
  и грузятся **отложенно** (`AlwaysDeferMcpTools`) через `tool_search`, а не
  объявляются inline в `/responses`. Схемы этих отложенных/MCP-инструментов —
  это отдельная механика захвата (перехват `tools/list` MCP-серверов или
  `tool_search` выдачи), не `response.create` фрейм. Для эталона профилей
  базовый inline-набор из 17 достаточен; deferred/MCP слой — опциональное
  расширение, если понадобятся его схемы. У Codex НЕТ инструмента `WebFetch`
  (это инструмент Claude-стека); веб у Codex — `web_search` (в inline-наборе).
- **Рамка цели (зафиксирована пользователем 2026-07-03): Native = оригинальная
  CLI-обвязка провайдера.** Система запускает каждого провайдера изначально с
  его родной обвязкой (системный промпт + системный тулинг + служебные
  сообщения) — считаем, что родные клиенты лучше всего подобраны под свои
  модели. Все остальные профайлы готовятся **редактированием Native-базы**:
  выбрасывается только универсальный балласт («на все случаи жизни»),
  всё важное для любого запроса сохраняется. Claude Agent SDK и Codex
  app-server выбраны как **канал управления** — только они позволяют менять
  системный промпт, тулинг и прочие опции, — но база остаётся базой
  клиента-провайдера, иначе теряется основа.
- **Claude: промпт собирается ПО РЕЖИМУ входа бинаря; Native-эталон — только
  интерактивный CLI** (эмпирическая матрица 2026-07-03, прогоны против
  локальной заглушки `ANTHROPIC_BASE_URL` на нашем провайдер-бинаре 2.1.195 и
  глобальном CLI пользователя 2.1.199): SDK не имеет своего сетевого стека —
  `query()` спавнит тот же самый бинарь `claude` (платформенный пакет
  `claude-agent-sdk-darwin-arm64`, user-agent `claude-cli/…`), но бинарь
  собирает системный промпт и inline-набор инструментов по режиму входа, и
  никакая опция SDK это не переключает: **SDK stream-json транспорт**
  (`cc_entrypoint=sdk-ts`, даже с пресетами `claude_code`) → SDK-identity
  («You are a Claude agent, built on Anthropic's Claude Agent SDK») + 9
  inline-тулов (~9.4k tok); **print-режим `-p`** → SDK-identity + 26 тулов;
  **интерактивный TTY (pty)** → «You are Claude Code, Anthropic's official
  CLI for Claude.» + полный inline-набор (29–30 тулов, ~23k tok: +
  AskUserQuestion, EnterPlanMode/ExitPlanMode, WebFetch, WebSearch, Task*,
  Cron*, Monitor, …) + служебное system-сообщение с каталогом агентов. Живой
  `/context` пользователя показывает System prompt ~4.1k tok — это базис
  ~1.5k + окруженческие секции (gitStatus, язык, настройки), появляющиеся в
  реальной сессии. Прежний вывод «пресеты claude_code дают полный CLI» —
  опровергнут: пресеты меняют только контент внутри SDK-режима сборки.
  Поэтому **capture запускает провайдер-бинарь интерактивно в настоящем pty**
  (`claude-interactive-cli-runner.ts`: драйвер на системном `python3`
  `pty.fork` — `script(1)` не доставляет piped stdin в pty, `expect` без
  активного дренажа блокируется на выводе Ink; boot-ожидание → ввод probe →
  submit → дренаж → самозавершение по таймеру), с авторизацией провайдер-home
  (`HOME`, `CLAUDE_USE_CLI_AUTH`) и предварительным акцептом
  onboarding/trust-диалога в `.claude.json`; таймаут capture-команды Claude
  поднят до 120s (pty-цикл не влезает в 30s дефолт прокси). Live
  Native-профиль сессий пока остаётся на SDK-пресетах `claude_code`
  (канал управления); приближение живого промпта к CLI-эталону — предмет
  Phase R на базе снятых эталонов.
- **Kimi: съём через reverse-forward мост, ACP с дефолтным агентом**
  (установлено 2026-07-03). **СТАТУС (2026-07-05, прямой приказ
  пользователя): Kimi УДАЛЁН из capture вместе с модулем `kimi-provider`.**
  Capture теперь обслуживает только нативные каналы Claude/Codex;
  reverse-forward мост (`capture-proxy-reverse.ts`), правило целей `kimi` и
  ветка `captureViaReverse` удалены. Материал для Phase R по Kimi — уже
  принятые дампы от 2026-07-03 (новые сняться не могут: ACP-канал ушёл вместе
  с модулем). Описание ниже сохранено как историческая проектная запись того,
  что было снято и почему. Прежний Kimi-«захват» был заглушкой — записывал
  только пути (`wire.jsonl`, который никто не пишет) и оркестратор завершал
  прогон `captured` с нулевым содержимым (ложный успех). «Wire» — это наш
  ACP JSON-RPC (клиент↔агент), в нём НЕТ нативного system prompt / схем
  инструментов: они только в HTTPS-запросе бинаря kimi к LLM-эндпоинту.
  Эмпирическая матрица (локальная base_url-заглушка на клоне `.kimi-code`,
  ноль токенов, kimi-code 0.18.0): интерактивный TTY, `-p` print и
  `kimi acp` с ДЕФОЛТНЫМ агентом шлют ИДЕНТИЧНУЮ нативную обвязку — system
  «You are Kimi Code CLI...» 14755 символов (~3.7k tok) + 23 нативных
  инструмента (~14.5k tok: Agent, AgentSwarm, AskUserQuestion, Bash,
  CreateGoal, Cron*, Edit, EnterPlanMode/ExitPlanMode, FetchURL, Glob, Grep,
  Read, Skill, Task*, TodoList, WebSearch, Write); print добавляет лишь
  auto-permission system-reminder; ACP == интерактиву байт-в-байт после
  нормализации timestamp. Значит pty не нужен — ACP-канал с дефолтным агентом
  и ЕСТЬ нативная обвязка. Но бинарь kimi (Mach-O) ИГНОРИРУЕТ proxy-env
  (`HTTP(S)_PROXY`/`ALL_PROXY`/`NODE_USE_ENV_PROXY` не действуют), поэтому
  вариант B (запрос доходит до вендора через наш транзит) реализован как
  **reverse-forward мост**: локальный HTTP-listener на 127.0.0.1, куда
  указывает `base_url` во ВРЕМЕННОМ клоне `~/.kimi-code` (config.toml +
  credentials + device_id; живой конфиг не мутируется); мост записывает
  совпавший запрос и форвардит его 1:1 на реальный `api.kimi.com` (TLS),
  переписывая только Host, релеит ответ. Эндпоинт — `api.kimi.com` +
  `/coding/v1/chat/completions` (не `api.moonshot.ai`, как было в устаревшем
  правиле). **Находка для Phase R:** живые Kimi-сессии сейчас запускают
  `kimi acp` с managed-агентом `codeai-managed-agent`, чей system.md — это
  CODEX-промпт из reference-проекта (`CODEX_NATIVE_SYSTEM_INSTRUCTIONS` +
  аддендум CodeAI, 7 инструментов), а не родная база Kimi — прямое нарушение
  рамки «Native = клиент-провайдер», отдельный вопрос к Phase R.
- **Артефакты**: набор
  `<timestamp>-<provider>-<model>-native-request.jsonl`,
  `<timestamp>-<provider>-<model>-native-request.diagnostics.jsonl` и
  `<timestamp>-<provider>-<model>-native-request.md` в Harness home logs.
  Основной JSONL содержит только записи `request_captured`, то есть
  захваченные upstream request payloads. Lifecycle, applied envelope,
  provider diagnostics и proxy events пишутся отдельно в diagnostics JSONL.
  Markdown — читаемый отчёт с тремя profile-relevant группами:
  `System Prompt`, `Tool Declarations`, `Developer Context: Permissions,
  Skills, Plugins`; строковые prompt/developer payloads печатаются обычным
  текстом с реальными переносами строк, а не JSON-escaped `\n`. Credential-
  заголовки редактируются по списку до записи; тело запроса не редактируется —
  это и есть полезный груз; артефакты локальные и помечены как sensitive.
- **UI**: карточка `Native Request Capture` в Settings -> General с
  кнопками per provider (как в reference), статусом и путями артефактов;
  явные коды ошибок (`tls_trust_failed`, `target_not_seen`, `timeout`,
  `provider_not_supported`). Capture — команда диагностики, не сохраняемая
  настройка; обычные ходы пользователя прокси не касаются.
  Codex-каталог capture повторяет picker-visible `model/list`: GPT-5.6 Sol,
  Terra, Luna, GPT-5.5, GPT-5.4, GPT-5.4 Mini и GPT-5.3 Codex Spark; удалённая
  GPT-5.2 не показывается. Для выбранной Codex-модели Core берёт
  нормализованный `providers.codex.reasoningByModel[model]` из Settings и
  передаёт его выделенному диагностическому адаптеру, поэтому native capture
  отправляет тот же `turn/start.effort` (включая `ultra` для Sol/Terra), а не
  `null` и не renderer-derived значение.
- Для Claude capture **дополняет** инвентарь из `init`: `init` даёт имена
  инструментов и версию CLI на runtime, capture — полные схемы и текст
  системного промпта для анализа и составления профилей.
- Эталоны — вход для анализа промпта (Phase R): какие разделы незыблемы
  (без них модель работает плохо), какие излишни для конкретных типов
  запросов (перечисления «на все случаи жизни» против важных поведенческих
  блоков). Методическая основа сравнения — reference-концепция

## Открытые вопросы (следующая часть обсуждения)

- **Универсальность системного промпта не доказана.** Тулинг деривируется
  из общего документа механически, но промпт — нет: модель провайдера может
  резко менять качество в зависимости от текста. Экспериментальный факт
  (CodeAI-Hub, проверка системных промптов на GLM 5.2; собственного
  системного промпта у GLM взять негде — CLI нет, десктопный ZCode закрыт):
  сравнивали системные промпты Claude и Codex, и промпт Claude дал заметно
  лучшее качество результата.
  Прежде чем фиксировать «мультипрофайлы» (один промпт на всех), нужна
  исследовательская работа: прогоны одинаковых задач по провайдерам с
  разными промптами и сравнение качества. Возможные исходы: (а) общий
  промпт работает достаточно хорошо; (б) слоёная модель — общее ядро +
  провайдер-специфичный аддендум в том же документе; (в) для каждого
  провайдера промпт и тулинг подбираются отдельно под каждую задачу.
  Решение принимает пользователь по результатам исследования.
- **Codex / Kimi: каналы применения.** Канал **получения** native-эталонов
  закрыт решением 5 (forward-транзит с записью запроса; для Codex —
  декодирование WS-фрейма, для Kimi — новая часть с preflight-риском доверия
  к CA). Открытым
  остаётся канал **применения** кастомного тулинга: у Codex нет per-thread
  управления инструментами (только процессные флаги `--disable`, см. аудит
  v1), у Kimi канал `agent.yaml -> tools:` существует, но был отложен из-за
  недоказанной привязки материализованных файлов к CLI. Фазы реализации для
  этих провайдеров в дорожную карту не входят до закрытия вопроса.

native пары (системный промпт + системный тулинг) от трёх провайдеров
