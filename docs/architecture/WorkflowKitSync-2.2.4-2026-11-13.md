# Синхронизация Workflow Kit 2.2.4 в Harness AI

Статус: спецификация и предложение scope `workflow-kit-sync-2.2.4-2026-11-13`.
Реализация начинается после выбора пользователем режима на карточке Workflow Kit.

## 1. Цель и согласование

Перенести Workflow Kit 2.2.4 из локального проекта
`/Users/oleksandroliinyk/VSCODE/Workflow_Kit` в Harness AI: синхронизировать
исходники и тесты, обновить установленный Kit этого репозитория, собрать и
опубликовать Harness AI с обновлённым Kit.

Поручение пользователя: «В текущем проекте нужно довести модуль workflow kit до
версии 2.2.4». После уточнения состава работы пользователь подтвердил:
«Всё верно, готов спецификацию и план».

Канонический процесс — управляемая секция [AGENTS.md](../../AGENTS.md).
Архитектура Kit — [WorkflowKit.md](workflow-kit/WorkflowKit.md), интеграция
Core — [WorkflowKitCoreRpc.md](workflow-kit/WorkflowKitCoreRpc.md).

## 3. Границы переноса

Все 12 модулей сверяются с донором. Целевая граница остаётся
`product-parts/core-runtime/clusters/project-workflow/modules/<module>`.
Kit остаётся частью Core Runtime; UI передаёт команды и отображает Core read models.

Переносить:

- параметр платформы `currentWorkflowPlatform(platform?)`, `install.platform`,
  `doctor.platform`; правила executable для win32/darwin/linux;
- разбиение реализации в `workflow-autopilot`, `workflow-git`,
  `workflow-integration`, `workflow-plan`, `workflow-kit` и `workflow-installer`;
- `KIT_VERSION = 2.2.4`, связанные проверки версии и контракты;
- новые и изменённые тесты: установка, Doctor, правила ОС, сценарий оркестрации,
  worktree, запуск процессов, пути и окружение Windows, предел времени host-команд;
- актуальные описания перенесённого поведения и происхождения синхронизации.

Адаптации Harness AI:

- Тесты и их помощники остаются в `src/**`, как требует владение модуля здесь;
  импорты донорских `test/**` переводятся обратно в `src/**`.
- Донорский `workflow-kit/tests.md` не добавляется: содержание отражается в
  `module.md`, без нового файла вне границы владения.
- Сборка остаётся `scripts/build-workflow-kit.mjs` и
  `vite.workflow-kit.config.ts`. Host-тест использует существующую Vite-сборку.
  Новая зависимость esbuild и донорская система сборки не нужны.
- Лимит Harness — 500 строк для файлов реализации. Перенесённое разбиение
  сохраняется; форматирование проверяется существующим профилем.
- В документах сохраняются локальные ссылки Harness и реальные пути `src/**`.
  Донорские ссылки на GitHub, возникшие из-за отсутствия документов в Workflow_Kit,
  не заменяют имеющиеся локальные документы.
- Файлы без содержательных изменений не переписываются только ради переноса.
  После адаптации сверить все модули; каждое оставшееся отличие объяснить.

Версии приложения Workflow_Kit и Harness AI не меняются. UI и служба
Workflow_Kit, native session controls, PTY, release-скрипты донора и его настройки
разработки не переносятся. Core/provider-контракты Harness сохраняются.

## 4. План реализации

План подаётся в `scope:propose`; JSON-вход хранится локально в
`.harness/runtime/workflow-kit-sync-2.2.4-plan.json`. После выбора режима Kit
создаёт машинный план в `.harness/plans/todo-plan.md`.

| ID | Результат | Зависимости | parallelSafe |
| --- | --- | --- | --- |
| T001 | Платформа, установщик и Doctor 2.2.4, связанные тесты | — | false |
| T002 | Разбиение модели плана и завершения scope | T001 | true |
| T003 | Синхронизация фасада Kit, scope/CLI и тестов процесса | T002 | true |
| T004 | Синхронизация Git, интеграции, autopilot и тестов оркестрации | T001 | true |
| T005 | Оставшиеся изменения тестов assignment, host, quality, recovery; итоговая сверка | T003, T004 | false |
| DOCS-R1 | Общая документация, дерево продукта и дайджест раунда | Все work | false |
| T006 | Обновление установленного Kit Harness с 2.1.1 до 2.2.4 | T005, DOCS-R1 | false |
| T007 | Сборка и проверка приложения macOS с новым Kit | T006 | false |
| T008 | Публикация main, тега и GitHub Release с zip приложения | T007 | false |

DOCS-R1 добавляет Kit автоматически. Отдельной QUALITY-задачи не требуется:
профиль уже CONFIGURED. Проверки входят в каждый коммит; самостоятельной задачи
«прогнать проверки» нет. T002/T004 и T003/T004 имеют независимые наборы файлов.
Рекомендуется sequential: обновляется сам механизм разработки, а сборка,
самообновление и выпуск последовательны. Метки отражают возможность отдельной
оркестрации при выборе пользователем этого режима.

Явное исключение из ориентира «до трёх функциональных файлов»: задачи переноса
охватывают указанные в машинном плане связанные исходники и регрессионные тесты
со своими `module.md`. Разбиение донора и его helper-файлы переносятся атомарно
внутри соответствующей задачи. Новые абстракции сверх донора не добавляются.

## 5. Проверки и критерии готовности

1. Все 12 модулей сравнены с зафиксированным донором; перенесённые исходники
   соответствуют 2.2.4, исключения ограничены разделом 3 и зафиксированы в итоге.
2. Проверены установка и повторное обновление проекта, сохранение пользовательских
   частей AGENTS/hooks и конфигурации, executable-правила, версия и manifest.
3. Полный набор тестов Kit проходит с адаптацией к структуре Harness;
   цикл scope/task/commit/DOCS, назначения, интеграция, recover и схемы CLI работают.
4. Существующие тесты Core RPC, provider workspaceContext, автопилота, паузы,
   выбора режима и plan read model проходят. При несовместимости исправляется
   общая граница в отдельной согласованной задаче; UI-эвристики не добавляются.
5. Сборка Harness создаёт `dist/workflow-kit/workflow.mjs` только с импортами
   Node builtins; smoke install/validate/doctor проходит во временном проекте.
   Хеш бандла Harness не обязан совпадать с донорским: сборщики и пути разные.
6. Установленный Kit Harness реально обновлён командой установщика: runtime и
   manifest согласованы, `doctor`, `validate`, `status`, `schema` и `recover`
   работают, активный план и история сохранены. Ручных правок управляемых файлов нет.
7. Новая SessionStart-доставка проверена отдельным запуском hook с параметрами
   Codex и Claude; для Claude сопоставлены все части и дайджест. Это проверка
   hook-контракта. Доставку в контекст живого провайдера подтверждает только новая
   сессия; старый чат не служит таким доказательством.
8. macOS-приложение из `release/mac-arm64/Harness AI.app` перезапущено после
   package:mac. Проверены подготовка проекта с Kit 2.2.4 и чтение состояния через
   Core. Моделирование правил Windows на macOS не считается живым Windows-тестом.
9. Перед публикацией проверены история на секреты и push-проверки; опубликованы
   main, тег даты сборки и Release с дайджестом и zip неподписанного приложения.

Коммит-проверки — текущий профиль Kit: architecture, lint, knip, typecheck,
tests, docs contracts, doc size и Markdown links. Перед пакетом также выполняются
`npm run quality`, `npm run check:dup`, `npm run check:security`,
`npm run check:links`. Сборки выполняются только в delivery-задачах.

## 6. Порядок обновления и выпуска

T006 сначала собирает бандл Harness 2.2.4 из синхронизированных исходников,
затем запускает `install --update` с этим бандлом и `--host harness` через Kit.
Установщик сам создаёт служебный `kit-update` коммит, не помечающий задачу DONE;
результат T006 фиксируется отдельным task-коммитом с доказательствами. Это
штатная транзакция установщика, без прямого git commit. Проверить продолжение
активного delivery-плана новым runtime. При незавершённой транзакции — `repair`.

В T006 создаётся `docs/evidence/WorkflowKitSync-2.2.4-2026-11-13.md` с версиями,
коммитами, хешами, перечнем адаптаций и результатами проверок; каталог документации
обновляется в том же коммите. После обновления никаких ручных правок runtime,
manifest, launchers, hooks или управляемой секции AGENTS.md.

T007 выполняет `npm run build`, затем `npm run package:mac`, проверяет наличие
пакета и его запуск. T008 публикует по
[ReleaseFixes-2026-11-04-2.md, раздел 8](ReleaseFixes-2026-11-04-2.md#8-публикация-на-github):
обычный push main в origin, тег `vYYYY.M.D` с суффиксом при повторе даты,
Release и zip через `ditto -c -k --keepParent`. Версия package.json неизменна.

Каждая delivery-задача начинается с подтверждения пользователя, записанного в
`task:start --confirmed`, как требует AGENTS.md. На этапе спецификации сборка и
публикация не запускаются. Приёмка записывается только по явному положительному
ответу пользователя; закрытие scope требует отдельной прямой команды.
