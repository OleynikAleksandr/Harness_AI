# Workflow Kit — режимы выполнения и оркестровка (предложение)

Статус: предложение для обсуждения, редакция 2 (2026-11-04). Не является
действующим контрактом: после согласования переносится в
`docs/architecture/workflow-kit/` и становится основой scope.

Источники:

- прогоны Harness AI на `Test_New_HarnesAI_001` и `Test_New_HarnesAI_002`;
- Workflow Pilot 0.6.11 / Kit 1.10.10, который переносится по смыслу:
  - выбор режима: `.harness/kit/lib/execution-mode.mjs`,
    `docs/modules/user-choice.md`;
  - роли: `.harness/kit/lib/role-protocol.mjs`;
  - оркестровка: `docs/modules/orchestrated-execution.md`,
    `packages/workflow-kit/docs/modules/orchestrated-plans.md`;
  - сайдбар: `docs/modules/desktop.md` («Дерево», «План»).

## 1. Проблема

Kit 2.0 знает одну папку, один план и одну задачу в работе.

- Нет выбора режима. Агент сам решает, звать ли субагентов, и зовёт их даже
  для последовательного плана.
- Исполнители не могут коммитить. Хук Kit общий для всех worktree, и
  `git commit` в worktree субагента отклоняется
  (`MANAGED_COMMIT_REQUIRED`). В прогоне 002 оркестратор перенёс файлы в
  main и закоммитил от себя: коммитов исполнителей и их проверок в истории
  нет.
- Нет параллельности: пока одна задача `IN_PROGRESS`, `task:start` другой
  невозможен.
- Git-идентичность Kit не формирует. Глобальная заглушка
  `Ваше Имя <you@example.com>` попала в коммит установки. Агенты с
  изолированным домашним каталогом её даже не видят, и оркестратор угадал
  имя сам.
- В сайдбаре Harness плана нет. Субагенты висят карточками под агентом, и
  их не связать с задачами.

## 2. Как это сделано в Workflow Pilot

1. Режим выбирает пользователь. Когда спецификация готова, агент вызывает
   `plan:mode-request` с рекомендацией и причиной. Приложение показывает
   карточку:
   - первой строкой рекомендация агента;
   - затем второй режим;
   - затем «Сначала доработать спецификацию».
   Нажатие записывает выбор (`plan:mode-choose`, вызывает только
   приложение). План создаётся в выбранном режиме, иначе
   `EXECUTION_MODE_MISMATCH`.
2. Сессия, запросившая режим, — владелец планирования. При `sequential`
   это роль «выполняет сам», при `orchestrated` — «Оркестратор».
3. `sequential`: эта сессия выполняет задачи по порядку в main. Роль
   прямо запрещает создавать исполнителей и назначения.
4. `orchestrated`: метки задач `parallel_safe` ставит оркестратор в плане.
   - Задачи с меткой `true` идут параллельно, если их пути не пересекаются.
   - Задачи с `false` идут по одной после всех предыдущих (барьер).
   - Обе категории выполняют исполнители в своих worktree. В main обычные
     задачи и DOCS не начинаются (`ORCHESTRATED_MAIN_READ_ONLY`).
   - Delivery выполняет оркестратор в main после интеграции всего.
     Отдельной задачи QUALITY в Kit 1.x нет.
5. Сайдбар: под карточкой агента — план с задачами, состоянием, меткой
   parallel/sequential и прогрессом «в main N из M». Начатая задача
   открывает сессию своего исполнителя.

## 3. Режимы выполнения

### 3.1 Метки задач

- Задача `work` получает `parallelSafe: boolean`, по умолчанию `false`.
- `true` требует конкретных путей в `files`: без glob, без `.` и без
  завершающего `/`.
- Две задачи совместимы, если:
  - обе `parallelSafe`;
  - ни одна не зависит от другой, даже транзитивно;
  - их пути не совпадают и не вложены друг в друга.
- У плана есть параллельная работа, если совместима хотя бы одна пара.
  Это вычисляет Kit, а не агент и не UI.

### 3.2 Режимы

- **`sequential`** — всю работу выполняет одна сессия, сама, по порядку, в
  main. Субагентов и назначений для задач плана нет. Метки `parallelSafe`
  сохраняются в плане, но игнорируются.
- **`orchestrated`** — сессия становится оркестратором. Каждая задача
  `work` выполняется отдельным исполнителем в своём worktree, и
  параллельная, и последовательная. Оркестратор раздаёт задачи, принимает
  результаты и интегрирует их в main.

Лимит одновременных исполнителей `maxWorkers` задаёт план, по умолчанию 3.

### 3.3 Выбор режима

Агент понимает задачу, пишет спецификацию и план с метками. Затем, вместо
`scope:create`, вызывает:

```text
scripts/workflow scope:propose --input <plan.json> \
  --recommended sequential|orchestrated --reason "…"
```

Kit проверяет план так же, как `scope:create`, но не создаёт scope. Он
сохраняет предложение `.harness/workflow/local/scope-proposal.json`
(поколение, digest плана, рекомендация, причина, варианты) и отвечает
вариантами:

| План | Варианты карточки |
|---|---|
| есть параллельная работа | рекомендация агента; второй режим; «Сначала доработать спецификацию» |
| параллельной работы нет | «Выполнить последовательно»; «Сначала доработать спецификацию» |

Рекомендация `orchestrated` без параллельной работы отклоняется
(`NO_PARALLEL_WORK`).

Harness Core видит предложение и показывает карточку в чате этой сессии.
По нажатию Core вызывает:

```text
scripts/workflow scope:choose --generation <N> --strategy <s> --note "<выбор>"
```

- Kit сверяет поколение и digest. Устаревший выбор —
  `PROPOSAL_CHANGED`, без записи.
- Kit создаёт scope из сохранённого плана с
  `execution: {strategy, maxWorkers, ownerSession}`.
- Выбор пользователя попадает в `approval` плана.
- Core отправляет агенту сообщение с выбором: что выбрано и что делать
  дальше.
- «Сначала доработать спецификацию» удаляет предложение. Агент получает это
  как сообщение пользователя.
- Ручной ответ пользователя в чат снимает карточку (как declined в
  Workflow Pilot).

Без Harness (терминал, `config.host` не `harness`) `scope:create` работает
как сейчас и создаёт `sequential`. В проекте Harness `scope:create`
отвечает `EXECUTION_MODE_REQUIRED` и называет `scope:propose`. Режим
меняется только новым scope: смена режима посреди плана не нужна.

## 4. Назначение исполнителю

### 4.1 Первый этап: привязка к worktree провайдера

Worktree исполнителю создаёт встроенный механизм субагентов провайдера, а
Kit к нему привязывается. Выбора вендора исполнителя пока нет: субагенты
Claude работают у оркестратора Claude, субагенты Codex — у оркестратора
Codex.

```text
scripts/workflow assignment:next
scripts/workflow assignment:create --task <ID>
scripts/workflow assignment:attach <id>      # в worktree исполнителя
```

- `assignment:next` (и recovery оркестратора) называет задачи, которые
  можно раздать сейчас, с учётом зависимостей, барьера, `maxWorkers` и
  путей. Решение «когда и что» принимает Kit.
- `assignment:create` в main выдаёт id и готовый текст поручения
  исполнителю: задача, критерии, файлы, первый шаг `assignment:attach`.
  Предусловия:
  - scope `ACTIVE`, стратегия `orchestrated`, нет транзакции и интеграции;
  - main чист, база = `HEAD`;
  - задача `TODO`, её зависимости `DONE` и являются предками базы;
  - одно активное назначение на задачу (`ASSIGNMENT_EXISTS`);
  - лимит и совместимость (`ASSIGNMENT_CAPACITY`, `ASSIGNMENT_BARRIER`,
    `ASSIGNMENT_CONFLICT`).
- Оркестратор запускает субагента встроенным механизмом провайдера
  (Claude: `Agent` с `isolation: "worktree"`) и передаёт текст поручения.
- `assignment:attach` проверяет, что это linked worktree того же
  репозитория, `HEAD` равен базе и дерево чисто. Затем записывает в
  назначение путь worktree и ветку. Ветку провайдера Kit не переименовывает.
- Установщик добавляет `.claude/worktrees/` в управляемый `.gitignore`.

Codex: если его субагенты не создают собственный worktree (проверяется в
первой задаче реализации), worktree создаёт Kit (`git worktree add -b
workflow/<id>`) внутри проекта в `.harness/worktrees/<id>`. Каталог
игнорируется и доступен песочнице Codex. Субагент получает этот путь как
рабочий каталог. Остальная механика та же.

### 4.2 Состояние

- Запись в main: `.harness/workflow/local/assignments/<id>.json`.
- Запись в worktree: `.harness/workflow/local/assignment.json`.
- Поля: `id`, `scopeId`, `taskId`, `iteration`, `worktree`, `branch`,
  `baseCommit`, `mode` (`attached`/`created`), `configDigest`, `phase`,
  `sourceCommit`, `integrationCommit`, `cleanup`.
- Повтор команды с тем же id сверяет входы и продолжает.

### 4.3 План исполнителя

`assignment:attach` строит план из базового коммита и делает служебный
коммит с ролью `assignment-plan` (только файл плана):

- scope `assignment-<id>`, одна задача — копия назначенной,
  `dependencies: []`, стратегия `sequential`;
- контракт неизменен: правка плана, конфигурации или файлов вне `files`
  задачи отклоняется (`ASSIGNMENT_CONTRACT`, `ASSIGNMENT_SCOPE`).

В worktree разрешены `status`, `recover`, `show-task`, `task:start`,
`commit --task`, `repair`, `task:block`, `assignment:status` и хуки.
Остальное — `ASSIGNMENT_READ_ONLY`, `pre-push` отклоняется.

Цикл исполнителя: `task:start` → работа → `commit --task` с проверками
задачи в его worktree → отчёт оркестратору с SHA. Хук общий, но журнал
транзакции у каждого worktree свой (`.harness/workflow/local`), поэтому
механизм управляемого коммита Kit 2.0 работает без изменений.

### 4.4 Окружение worktree

Если проверкам задачи нужны зависимости, статус `NEEDS_SETUP`:

- `assignment:setup --id <id>` выполняет команду подготовки из профиля
  качества стека (для `node` — `npm ci` по lock-файлу);
- `node_modules` main не копируется и не связывается;
- задача без назначенных проверок (например, DOCS) подготовки не требует.

### 4.5 Статусы

| Статус | Когда |
|---|---|
| `ASSIGNED` | создано, исполнитель ещё не привязался |
| `NEEDS_SETUP` | окружение не готово |
| `READY` | можно начинать |
| `RUNNING` | задача исполнителя начата |
| `READY_FOR_INTEGRATION` | есть коммит `implementation` с пройденными проверками |
| `INTEGRATED` | принят в main |

## 5. Порядок работы оркестратора

1. Задача `QUALITY` (если есть) — оркестратор в main: она пишет
   конфигурацию Kit, которая живёт только в main.
2. Задачи `work` — только исполнители (`ORCHESTRATED_MAIN_READ_ONLY` на
   `task:start` в main). DONE задачи — только коммит с ролью
   `integration`.
3. `DOCS-<раунд>` — исполнитель, как в Workflow Pilot, после интеграции
   всех задач раунда. Вариант на обсуждение — оркестратор в main (вопрос 1).
4. `delivery` — оркестратор в main, когда все задачи DONE и назначений нет
   (`DELIVERY_NOT_READY`).

## 6. Интеграция

```text
scripts/workflow integration:start --id <assignment> --source <sha>
scripts/workflow integration:continue --id <assignment>
```

Kit доказывает источник (`INTEGRATION_HISTORY`, `INTEGRATION_UNCHECKED`):

- история `base..source` — ровно коммит `assignment-plan` и коммиты
  `implementation` этой задачи с верными trailers;
- в diff нет служебных файлов Kit;
- квитанция проверок исполнителя относится к дереву `source`, все проверки
  `PASSED`.

Шаги:

1. `git merge --no-commit --no-ff <source>`.
2. План исполнителя заменяется кандидатом общего плана: задача `DONE`,
   `operationId`, `sourceCommit`.
3. Изменения вне `files` задачи — `INTEGRATION_SCOPE`.
4. Коммит `merge: <title>` с двумя родителями, проверки задачи на
   объединённом результате, trailers `Workflow-Role: integration` и
   `Workflow-Source`.

Ошибки:

- Конфликт — фаза `CONFLICT`. Оркестратор разрешает его в пределах файлов
  задачи и вызывает `continue`. Ours/theirs Kit сам не применяет.
- Проверки упали — `CHECKS_FAILED`. Состояние слияния сохраняется, после
  исправления — `continue`.
- Журнал `.harness/workflow/local/integration.json` блокирует другие
  записи. Повтор завершает уже созданный коммит без второго merge и
  `reset --hard`.

После `INTEGRATED` Kit удаляет worktree (`git worktree remove` без force)
и влитую ветку (`git branch -d`). Отказ даёт `cleanup: PENDING`, а
`assignment:cleanup` доделывает. Сверка истории принимает двухродительские
коммиты только с ролью `integration`.

## 7. Git-идентичность

Идентичность — это имя и почта автора, которые Git записывает в каждый
коммит («кто сделал»). Сейчас Git берёт их из глобальной настройки
пользователя `~/.gitconfig`. На этом компьютере там заглушка `Ваше Имя`.
Агенты запускаются с отдельным домашним каталогом и не видят даже её.

Без новых настроек Harness:

1. Установщик Kit (его запускает Harness Core с настоящим домашним
   каталогом) берёт идентичность из локального конфига репозитория, иначе из
   глобального.
2. Заглушки отклоняются (`GIT_IDENTITY_PLACEHOLDER`): пустые значения,
   `you@example.com`, домены `example.*`/`invalid`/`localhost`, имена
   `Your Name` и `Ваше Имя`.
3. Найденная идентичность записывается в локальный конфиг репозитория. Все
   worktree читают его через общий каталог Git, поэтому оркестратор и
   исполнители подписывают коммиты одинаково, независимо от домашнего
   каталога агента.
4. Каждый коммит Kit передаёт идентичность явно (`-c user.name/-c
   user.email`) и проверяет её перед транзакцией.
5. Если настоящей идентичности нет, коммит Kit отвечает
   `GIT_IDENTITY_REQUIRED` с готовой командой
   `git config --global user.name/user.email`. Пользователь выполняет её
   один раз на компьютере, Доктор применяет её к проекту.
6. Агентам запрещено задавать идентичность самим (правило управляемой
   секции `AGENTS.md`).

## 8. Роли и правила агента

Управляемая секция `AGENTS.md` и recovery получают роли по образцу
`role-protocol.mjs`:

- **планирование** (scope нет): спецификация, план с метками,
  `scope:propose`, конец хода до выбора пользователя;
- **выполняет сам** (`sequential`): задачи по порядку в main, субагентов и
  назначений для задач плана не создавать;
- **оркестратор** (`orchestrated`): `assignment:next` → `assignment:create`
  → запуск субагента с текстом поручения → ожидание SHA →
  `integration:start`; обычную реализацию в main не выполнять;
- **исполнитель** (worktree назначения): `assignment:attach` →
  `task:start` → `commit --task` → отчёт с SHA; main, план и чужие задачи
  не трогать, вложенных исполнителей не создавать.

## 9. Harness

### 9.1 Карточка выбора режима

- Core наблюдает `scope-proposal.json` и строит модель карточки: вопрос,
  варианты, рекомендация, поколение. Renderer её только показывает.
- Вид как в Workflow Pilot: рекомендуемая строка первой с пометкой
  «(рекомендую)» и залитой кнопкой, под ней причина. Подсказка «или
  напишите ответ в чат».
- Нажатие идёт в Core, Core вызывает `scope:choose` и отправляет агенту
  сообщение с выбором.

### 9.2 План в сайдбаре

- Под карточкой агента проекта показывается активный план, в любом режиме.
  Карточка подписана «Агент», в `orchestrated` — «Оркестратор».
- Верх: название scope, состояние, прогресс «выполнено N из M».
- Строки: значок состояния, ID, название, метка «параллельно» или
  «последовательно» (только в `orchestrated`). Текущая задача подсвечена.
- Динамика: Core перечитывает статус Kit после команд Kit и изменений
  файла плана и отправляет обновлённую модель.
- В `orchestrated` строка задачи с исполнителем открывает его сессию.
  Привязанные к задачам исполнители не дублируются карточками под
  оркестратором. Субагенты вне плана (исследование, поиск) остаются под
  агентом, как сейчас.
- Привязку исполнитель ↔ задача вычисляет Core: рабочий каталог
  субагента, известный из его сессии, совпадает с `worktree` назначения
  Kit. Renderer ничего не сопоставляет.

### 9.3 Прочее

- Workflow host и Core RPC получают `assignments` и `scopeProposal` в
  статусе.
- Автопилот в `orchestrated` продолжает ход оркестратора, когда Kit
  сообщает `READY_FOR_INTEGRATION` или готовность следующих задач.
- Новые и открытые проекты Harness ставят `config.host: "harness"`.

## 10. Порядок реализации (предварительно)

Два релиза, по одному серьёзному изменению:

**Релиз A — режимы и план в сайдбаре.**

1. Kit: `parallelSafe`, вычисление параллельной работы, `scope:propose`,
   `scope:choose`, `EXECUTION_MODE_REQUIRED`, роли «планирование» и
   «выполняет сам».
2. Kit: Git-идентичность (раздел 7).
3. Core: модель карточки выбора, вызов `scope:choose`, сообщение агенту.
4. Renderer: карточка выбора.
5. Core и renderer: план с задачами и динамикой в сайдбаре.
6. Мелкие замечания прогонов:
   - `.harness/sessions/` и `.claude/worktrees/` в управляемом
     `.gitignore`;
   - ложный дрейф качества без `package.json`;
   - `product-tree.json` как документ для DOCS;
   - остатки `pending-*.json`;
   - `inspect --format text`.

**Релиз B — оркестровка.**

1. Kit: назначения, план исполнителя, защита контракта в worktree.
2. Kit: интеграция, журнал, проверки на объединённом результате, очистка.
3. Kit: роли оркестратора и исполнителя, recovery, `assignment:next`.
4. Проверка Codex: создаёт ли его субагент worktree; иначе worktree Kit.
5. Core и renderer: привязка исполнителей к строкам плана.
6. Сценарный тест на настоящих worktree: два параллельных исполнителя,
   барьер, конфликт, падение объединённых проверок, повтор после сбоя.
   Затем сборка и проверка на тестовом проекте.
